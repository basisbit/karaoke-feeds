# Running a karaoke feed: operator guide

This guide is for the person who looks after the songs of a feed. You need a terminal, but no programming.
Related guides: [signing.md](signing.md) (keys and signatures), [hosting.md](hosting.md) (web server).

## 1. How it works

You work in a normal songs folder, the way you always have. A tool, `kfeed`, turns that folder into a second folder that goes onto the web server.

```
my-feed/
  feed-config.json     settings of the feed (name, contact, keys)
  removed.txt          list of withdrawn songs (takedowns)
  songs/               YOU EDIT THIS: one folder per category, song folders inside
  public/              GENERATED by kfeed. Upload it. Never edit it by hand.
```

`public/` contains `feed.json`, `catalog/`, `blobs/` and (for signed feeds) `sig/`. The file names in there are checksums, which is why they look unreadable. You never add, rename or delete anything in `public/` yourself. Every change is made in `songs/`, followed by one `kfeed build`.

The cycle is always the same:

```
1. change something in songs/      (add, edit or delete a song folder)
2. kfeed build my-feed             (rebuilds public/ and tells you what changed)
3. kfeed verify my-feed/public     (optional check)
4. upload public/                  (see hosting.md)
```

## 2. Get the tool

There are no downloads yet. Build it from this repository with Go 1.22 or newer:

```
cd tool
go build -o kfeed .
```

The result is one file, `kfeed` (`kfeed.exe` on Windows), without further dependencies. Copy it wherever you like.

## 3. Create a feed

```
kfeed init my-feed
```

This creates the folder with a settings template. Open `my-feed/feed-config.json` and fill it in:

| Field | Meaning |
|---|---|
| `name` | Name of the feed as players see it. Required. |
| `description`, `homepage` | Optional text and link. |
| `operator.name` | Who runs the feed. Required. |
| `operator.contact` | `mailto:` or `https:` address for questions and **takedown requests**. Required, and it must be read by someone. |
| `songs` | Where the songs folder is. Default `songs`. May point elsewhere, for example to an existing git checkout: `"../my-songs-repo"`. |
| `output` | Where the published folder goes. Default `public`. |
| `keys` | Public keys if the feed is signed. Leave `[]` for now; see [signing.md](signing.md). |
| `mirrors` | Web addresses of complete copies of the feed, if there are any. |
| `url` | Optional: the public address of `feed.json`, shown on the feed's web page (section 10). |
| `private` | Optional: `true` makes it a feed for members only, see §11. |
| `catalogs` | Optional names and ids for categories, see §8. |

The tool refuses unknown field names, so a typo is reported instead of silently ignored.

## 4. Add a song

1. Create a folder for the category if it doesn't exist yet: `songs/Rock/`. Every folder directly inside `songs/` is one category that players can subscribe to.
2. Put the song folder inside, as you would for the game: `songs/Rock/Artist - Title/` with the txt, the audio file and optionally cover, background and video. Deeper nesting is fine.
3. Add the license information (next section).
4. Run `kfeed build my-feed`.

Only files that the txt refers to (`#MP3`/`#AUDIO`, `#COVER`, `#BACKGROUND`, `#VIDEO`, `#VOCALS`, `#INSTRUMENTAL`) are published, plus a `license.txt` if the folder has one. Anything else in the folder is ignored. The txt and all other files are published byte for byte; the tool never rewrites them.

A folder may contain several txt files that share media, for example a solo and a duet version. Each txt becomes its own song.

### License information

Every song folder needs a file `feed-meta.json` that says under which license each file may be distributed. Without it the song is still published, but games hide it by default, and a feed with such songs can't become a default feed of a game.

One license for everything in the folder:

```json
{
  "licenses": {
    "*": {
      "spdx": "CC-BY-4.0",
      "attribution": "'Song Title' by Artist Name",
      "source": "https://artist.example/song-title"
    }
  }
}
```

Different licenses for different files (typical: music by the artist, notes by a community member):

```json
{
  "licenses": {
    "audio": { "spdx": "CC-BY-NC-3.0", "attribution": "'Song Title' by Artist Name", "source": "https://artist.example/song-title" },
    "cover": { "spdx": "CC-BY-NC-3.0", "attribution": "Cover art by Artist Name", "source": "https://artist.example/song-title" },
    "txt":   { "spdx": "CC-BY-SA-4.0", "attribution": "UltraStar notes by Creator Name", "source": "https://creator.example/" },
    "*":     { "spdx": "CC0-1.0" }
  },
  "age": 12
}
```

| Field | Meaning |
|---|---|
| key (`"audio"`, `"txt"`, …) | Which file the license is for: `txt`, `audio`, `vocals`, `instrumental`, `video`, `cover`, `background`. `"*"` applies to every file without its own entry. |
| `spdx` | The license as an [SPDX identifier](https://spdx.org/licenses/), e.g. `CC-BY-4.0`, `CC-BY-NC-SA-3.0`, `CC0-1.0`. Required. |
| `url` | Link to the license text. Filled in automatically for Creative Commons identifiers; required for anything else. |
| `attribution` | The credit line games show. Strongly recommended; most CC licenses require credit. |
| `source` | Where you got the file, as proof of the license. Strongly recommended. |
| `age` | Optional minimum recommended age for the song, in years. |

`kfeed init` puts a `feed-meta.example.json` into the feed folder to copy from. You are responsible for the licenses you declare; the tool cannot check them.

## 5. Build and read the report

```
kfeed build my-feed
```

Example output:

```
Built feed "My Feed" → my-feed/public
  sequence 1794618036, UNSIGNED
  catalog rock                        12 songs     95.3 MB
Changes since the last build:
  + added (1): artist-new-song
  ~ changed (1): artist-old-song
  - delisted (clients hide them, cached files stay) (1): artist-gone
Hidden by default in clients, no license declared (1): somebody-something
NOT PUBLISHED, fix these (1):
  ! Rock/Broken/song.txt: the audio file "song.mp3" is missing
Warnings (1):
  - Rock/Other/song.txt: the background file "bg.jpg" is missing; published without it
```

- **added / changed / delisted / withdrawn** is what players' games will do after the upload. Read it before you upload. If it lists something you didn't intend, fix the songs folder and build again.
- **NOT PUBLISHED** songs have a problem that would break them for players. They stay out of the feed until fixed.
- **Warnings** don't stop a song from being published.
- `kfeed build my-feed --dry-run` shows the report without changing `public/`.
- Building again without changes writes no new feed. It only removes the song list and signature of the build before the last one, which are kept for one extra build so that games in the middle of an update still find them.

Each song gets an **id**, made from artist and title (`artist-old-song`). Games use the id to recognise a song across updates, so playlists and favourites keep working.

## 6. Change a song

Edit the files in the song folder (fix the timing in the txt, replace the cover, add a video) and build. The song appears under "changed"; games download only the files that differ.

**If you change artist or title in the txt, the id changes too**, and games would see a removed song and a new one. The report notices this and prints a `Renamed?` hint. To keep it one song, add the old id to the song's `feed-meta.json`:

```json
{ "previous_ids": ["artist-old-title"], "licenses": { ... } }
```

To fix an id for good, independent of artist and title, set it yourself: `"id": "my-stable-id"` (lowercase letters, digits, `.`, `_`, `-`). In a folder with several txt files use `"ids": { "Song [DUET].txt": "artist-song-duet" }` instead. You must set ids yourself when artist and title contain no Latin letters or digits, or when two songs have the same artist and title.

## 7. Remove a song

There are two kinds of removal. Choose deliberately.

| | Delist | Withdraw (takedown) |
|---|---|---|
| Use it when | you no longer want to offer the song | the song must go: rights problem, wrong license, takedown request |
| What you do | delete the song folder, build | delete the song folder **and** add its id as a line in `removed.txt`, build |
| In players' games | the song is hidden; files already downloaded stay on disk | the song is removed and its downloaded files are deleted (signed feeds only; in unsigned feeds it is just hidden) |
| Reversible | yes, put the folder back | the id can never be used again |

`removed.txt` takes one id per line; text after `#` is a comment, which is a good place for date and reason:

```
artist-problem-song     # 2026-11-14 takedown request by the label
```

After withdrawing, the build report lists the files to delete from servers, mirrors and CDN caches. See "Takedown" in [hosting.md](hosting.md); the takedown is not complete until that is done. The old song list, which still names the withdrawn song, stays in `public/` for one more build: run `kfeed build` a second time and upload again to remove it right away.

As a safety net, the build stops if more than a fifth of the published songs disappeared at once (for example because a drive wasn't mounted). If that was intended, repeat with `--allow-mass-removal`.

## 8. Categories

Each folder directly inside `songs/` is a category ("catalog"). Its id is made from the folder name (`Pop Songs` → `pop-songs`), and players' subscriptions refer to that id. **Renaming the folder changes the id and players lose the subscription.** To rename safely, or to add translated names, pin the id in `feed-config.json`:

```json
"catalogs": {
  "Pop & Chart Hits": { "id": "pop-songs", "names": { "de": "Pop & Charts" } }
}
```

A song belongs to exactly one category. For groupings across categories (duets, a season, a language) use the txt headers `#EDITION`, `#GENRE`, `#LANGUAGE` and `#TAGS`.

## 9. Check and publish

```
kfeed verify my-feed/public                  check the folder before uploading
kfeed verify https://feed.example.org/       check what players actually get
```

`verify` reads the feed the way a strict game would and reports every problem. Add `--full` to download and check every single file. Then upload as described in [hosting.md](hosting.md).

## 10. The web page of your feed

`kfeed build` also writes a web page into `public/`: `index.html`, `index.css`, `index.js`, and one `songs-<category id>.html` per category. Whoever opens your feed's address in a browser (`https://feed.example.org/`) sees:
- what it is: name, description, number of songs and size;
- how to get the songs, with a ready-to-copy `kfeed sync` command;
- the categories with their songs: for feeds of up to 100 songs directly on the page, for bigger feeds on one page per category with a filter box (a category of 10,000 songs is about 1 MB, compressed about 85 KB);
- the licenses;
- your contact for takedown requests and the signing key;
- links to the guides for running a feed.

It loads nothing from other websites (no fonts, scripts or images from elsewhere) and sets no cookies, so it needs no cookie banner and sends no visitor data to third parties. It adapts to phones and to light or dark mode.

The page is rebuilt on every `kfeed build`; don't edit it, your changes would be overwritten. To show the exact public address in the commands, set it in `feed-config.json`:

```json
"url": "https://feed.example.org/feed.json"
```

Without it, the page shows the address the visitor actually used, which also works for LAN copies and USB sticks.

## 11. Private feeds (members only)

To limit a feed to certain people (members of a club, paying subscribers, testers), set in `feed-config.json`:

```json
"private": true
```

- **Every person gets a personal address** with a random token in it, for example `https://feed.example.org/s/k3Vq…/feed.json`. The web server only answers addresses whose token is on its list. Setting that up is the server admin's part: section 9 of [hosting.md](hosting.md).
- **The feed must be signed** ([signing.md](signing.md)), and `mirrors`, `url` and `moved_to` must stay empty; `kfeed build` checks this. The reason: `feed.json` is the same file for everybody, so it can't contain anybody's address. And only with a signed feed can a person move to a new address when their token is replaced.
- **The web page** tells visitors that their address is personal, and shows a command that keeps the address out of the shell history.
- **Games need no special support.** Any game that reads feeds reads a private one.

How people get their address is up to you: by mail, or on your website after a login. To end someone's access, the admin removes their token. Songs they already downloaded stay with them: this controls who can download, it is not copy protection.

**Check the licenses.** Charging for access is a commercial use. Songs under a NonCommercial (NC) license very likely can't be part of a paid feed; `kfeed build` doesn't check this for you. The web page lists the licenses of the feed.

## 12. Problems and what to do

| Message | What to do |
|---|---|
| `set "operator.contact" to a real mailto: or https: address` | Fill in `feed-config.json`. |
| `unknown field "…"` | Typo in a field name of `feed-config.json` or `feed-meta.json`. |
| `the audio file "…" is missing` | The txt names a file that isn't in the folder. Fix the `#MP3`/`#AUDIO` line or add the file. |
| `file name "…" contains one of / \ : * ? " < > \|` (or similar) | The name would not work on every operating system. Rename the file and the reference in the txt. |
| `has extension "…", which is not allowed for role …` | Only common audio, video and image formats can be published. Convert the file. |
| `no valid id … set "id"` | Artist and title give no usable id. Set `"id"` in `feed-meta.json` (§6). |
| `the id "…" is already used` | Two songs with the same artist and title. Give each its own `"id"`. |
| `is listed in removed.txt but its song is still in the songs folder` | Delete the song folder, or take the line out of `removed.txt`. |
| `… published songs disappeared` | Check that the songs folder is complete. If intended: `--allow-mass-removal`. |
| `this feed is signed: pass --key` | See [signing.md](signing.md). |
| `is not empty and has no feed.json; refusing` | The output folder is not a feed. Check `output` in `feed-config.json`. |
| `a private feed must be signed` / `can have no "mirrors", "url" or "moved_to"` | See §11. |

## 13. Good to know

- **Back up** `songs/`, `feed-config.json`, `removed.txt` and your keys. `public/` can always be rebuilt.
- `public/` normally takes no extra disk space: the big files are hard links to the files in `songs/`. Use `--copy` if both folders are on different drives or you prefer real copies. With hard links, build again after every change in `songs/` before you serve or upload `public/`.
- Every build reads all files to compute checksums. With tens of gigabytes that takes a while.
- Automation: `kfeed build` works in CI (for example on every push to a songs repository). The key can be given with the environment variable `KFEED_KEY` (the file name) or piped in with `--key -`; see "Where the key comes from" in [signing.md](signing.md).
- Not in the tool yet: alternative qualities of a file (e.g. video in 480p and 1080p), separate preview clips, and a graphical interface.
